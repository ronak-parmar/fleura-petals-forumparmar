# Project context — Fleuréa Petals field project

TY B.Sc. (Computer Science) field project: a flower-ordering web app for Fleuréa Petals,
plus the polished project report (`report/Project_report.docx`) documenting it. Two parallel
tracks in this one repo:

1. **The report** (`report/`, `database/`, `diagrams/`, `mockups/`, `tests/`) — finished.
2. **The actual app** (`app/` frontend + `backend/` API) — a real build, in progress.
   `database/schema.sql` + `functions.sql` + `seed.sql` and the 15 `mockups/screens/*.html`
   were written as report figures first, but they are also the real schema and real pixel
   design for `app/` — treat them as authoritative, not just illustrative.

## Non-obvious facts

- **Single source of truth = `report/source.md`.** Never hand-edit `report/report.html` or
  `Project_report.docx` — they are generated by `scripts/build-report.js` and
  `scripts/build-docx.js`. Workflow: edit source → build report.html → user reviews →
  build docx on request. Don't rebuild the docx on every change.
- **Figures** are HTML in `diagrams/` and `mockups/`, rendered to PNG via headless Chrome
  (`scripts/render-figures.js`). Figure number → filename map: `scripts/lib/figures.js`.
  After editing any diagram/mockup, re-render before rebuilding the report.
- The build scripts use **only Node's standard library** — a hand-written ZIP writer
  (`scripts/lib/zip.js`) and a small Markdown parser (`scripts/lib/markdown.js`). No npm.
- **Design system** comes from the original static site (`reference/test.html`): palette
  Ivory / Blush / Rosewood / Sage / Gold Thread / Ink; display serif + humanist sans;
  ribbon motif. Kept in `mockups/shared/fleurea.css` and `diagrams/diagram.css`.
- The report/TOC structure must follow the college template in `reference/` — Chapters 1–8,
  References and Appendix count as chapters 7 and 8.
- **Names used in examples:** admin/owner = **Forum Parmar** (`forum` / `petals123`);
  example customers = **Beena Parmar** and **Ronak Parmar**.
- Stack: Next.js (React) · ASP.NET Core Web API · PostgreSQL · VS Code. **No payment
  gateway** — pay on delivery. Products have a `nature` (`everlasting` / `fresh`) that
  drives the shop filter and the checkout delivery-date rule.
- The API calls **PL/pgSQL functions** (`database/functions.sql`), not inline SQL —
  `fn_place_order` re-prices every order from the DB.
- Tests are documentation only (`tests/test-cases.md` page-by-page, `tests/Fleurea.http`).
  The user declined a real xUnit project — do not add one.
- **`app/FOUNDATION.md`** is the reference for the Next.js build — design tokens, every shared
  component's props, the full `lib/api/client.ts` function list, and the rule that **every
  page calling `client.ts` must be a Client Component** (`"use client"`) because there's no
  real backend yet — the mock "database" (`lib/api/fixtures.ts`) is just in-memory JS state
  that has to stay in one browser runtime, or e.g. admin wouldn't see orders customers place.
  Read it before touching anything under `app/`.
- `app/`'s `lib/api/client.ts` is a **swappable data layer**: every function has a `mock`
  branch (enforces the same business rules as `database/functions.sql`) and a stubbed `live`
  branch behind `NEXT_PUBLIC_API_MODE`. When the real ASP.NET Core backend exists, only that
  file changes — no page/component rewrites.
- **Node/npm on this machine:** two Node installs are on PATH; the first one found
  (`C:\nvm4w\nodejs`) is broken and throws `EPERM ... srv_admin` on any npm/npx call. Always
  run `export PATH="/c/Program Files/nodejs:$PATH"` before any `npm`/`npx` command.
- **Next.js is pinned to 16.3.4** in `app/package.json` — the `latest` tag (16.3.5) has no
  published Windows (`@next/swc-win32-x64-msvc`) binary, so installing/building it fails.
  Don't blindly bump to `latest` without checking the platform binary exists first.
- Pages using `useSearchParams()` (filters, deep links) need a `<Suspense>` boundary around
  the part that calls it, or `next build` fails — this bit multiple pages during the build.
- **E2E tests exist:** `app/tests-e2e/*.spec.ts` (Playwright, 36 tests covering clicks/redirects/
  forms across all page groups). Run with `npx playwright test` — config points at the system
  Chrome (`channel: "chrome"`) instead of Playwright's own bundled Chromium, because this
  network's TLS-intercepting proxy blocks Playwright's browser download (`SELF_SIGNED_CERT_IN_CHAIN`).
  Tests assume the dev server is already running on `:3100`.
- Two real bugs were found and fixed via this e2e suite (both were invisible to static
  screenshots — only showed up when actually clicking through flows):
  1. `checkout/page.tsx` — placing an order called `cart.clear()` before navigating to the
     confirmation page; clearing the cart raced the page's own "empty cart → redirect to
     /cart" guard, sometimes overriding the intended navigation. Fixed with a
     `navigatingAwayRef` guard.
  2. `account/page.tsx` — the customer token was read via a `useEffect` (starting as
     `undefined`), which let a stale "not signed in" rejection from `useAsync` leak through
     and clear a session that had *just* become valid — bouncing a freshly-registered/logged-in
     customer straight back to `/account/login`. Fixed by reading the token synchronously via
     a lazy `useState` initializer instead.
- Minor known nit (not fixed, low priority): `client.ts`'s `myOrders()` mock always includes
  the seeded order `FP-2026-000042` for any logged-in customer, not just Beena.
- **`backend/src/Fleurea.Api`** — the real ASP.NET Core Web API, built against
  `database/functions.sql` and `app/src/lib/api/client.ts`'s `live*` branches as the two
  sources of truth, **without a live Postgres instance** (that's still not set up on this
  machine — see `database/README.md`). It builds clean (`dotnet build`) but has never been
  run end-to-end. Read `backend/BACKEND_FOUNDATION.md` before touching it — it documents the
  `Db` helper (calls `fn_*` functions only, no inline SQL), the shared `Dtos`/`Mappers`, the
  `ApiExceptionMiddleware` + `PgErrorCodes` error-shape convention, and JWT auth
  (`Auth/CurrentUserExtensions`: `User.CustomerId()` / `User.AdminId()`).
- All 28 routes `client.ts` calls in live mode are implemented, across 13 controllers built
  by 5 parallel agents against that shared foundation (same pattern as the frontend build).
  `functions.sql` grew several functions beyond what the report originally illustrated —
  needed once real DTOs/routes forced every gap into the open: `fn_admin_get_order`,
  `fn_get_customer_orders`, `fn_get_customer_custom_requests`, `fn_admin_list_custom_requests`,
  `fn_admin_get_custom_request`, `fn_admin_list_enquiries`, `fn_get_customer_by_email`,
  `fn_get_customer_by_id`, `fn_get_addresses`, `fn_add_address`, `fn_get_admin_by_username`,
  `fn_touch_admin_login`, `fn_admin_list_products`. Several existing functions were also
  reshaped to return a consistent joined shape (`fn_get_order`, `fn_admin_list_orders`,
  `fn_get_product_by_slug`, `fn_upsert_product`, `fn_set_product_availability`,
  `fn_get_categories`, `fn_get_products`) so one `OrderMapper`/`ProductMapper` in C# could
  read every order-/product-returning function's row without special-casing. `seed.sql` was
  extended with real bcrypt password hashes (admin `forum`/`petals123`; Beena and Ronak both
  `password123`) and directly-inserted seed rows for order `FP-2026-000042` and custom
  request `FP-CR-2026-000007`, matching `app/src/lib/api/fixtures.ts` exactly.
- **Still open**: getting a local PostgreSQL instance actually running on this machine (the
  portable-zip download from EnterpriseDB is blocked on this network; `winget` has
  PostgreSQL 17/18 available but that's an admin/UAC service install, not yet approved).
  Until that's resolved: no live request has ever hit this backend, so treat it as
  "compiles clean against the documented contract," not "verified correct." First real
  test once Postgres exists: run `schema.sql` → `functions.sql` → `seed.sql`, start the API,
  hit a few routes in `tests/Fleurea.http`, then flip `app/.env`'s `NEXT_PUBLIC_API_MODE` to
  `live` and re-run the 36 Playwright tests against the real stack.
